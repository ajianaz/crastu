| 25 | 2026-11-11 | MCP agent names are self-declared labels for now; processes of the same OS user are trusted. Token pairing per agent comes in P1 (#15) before per-agent overrides can be set in Settings. Update 2026-11-12 (#15, slice 1): enforced in the host. `crastu agents add NAME` issues a token (`crastu_` plus 32 random bytes as hex) that is shown once; the host keeps only its SHA-256 hash, in the `agents` table of `crastu.db`. The shim sends the token from the environment variable `CRASTU_AGENT_TOKEN` (never an argument) with every call and the host resolves it to the agent, ignoring the declared name. Per-agent overrides apply only to paired agents; an unpaired caller always gets the defaults and the activity log marks it as unpaired. A token that is presented but unknown, rotated or revoked is an error, never a silent downgrade. `agents revoke` and `agents rotate` act on the next call. The user keeps the plain token in the MCP client's configuration; Keychain storage and the Settings, Agents screen are the next slices. Update 2026-11-12 (owner): agent tokens are not stored in the Keychain for the shim to look up by agent name. A lookup by name lets any process of the same user run `crastu mcp --agent NAME` and receive that agent's token without holding it (the `crastu` binary that writes the entry reads it back without a prompt), which is exactly what pairing exists to stop. The token stays where the user puts it: the client's configuration `env` block (`CRASTU_AGENT_TOKEN`), never an argument of `crastu mcp`. That block is a plain file other processes of the same user can read too; the difference is that a lookup by name would make the name itself the credential again, while a token has to be read from that agent's own configuration. A Keychain option can come back only with a design that ties the item to one client, not to a name. |

| 30 | 2026-11-12 | Offline mode has one gate: `NetGate` in `crastu-core` (no I/O, cheap to clone, shared flag). Every outbound request type (model download, update check, provider call, sync) must call `gate.check(what, url)` before it opens a socket; with Offline on it returns an error that names what and which host (never path, query or credentials) and the gate keeps a bounded list of refusals for the activity log. The switch is the setting `network.offline` (off by default) and the environment variable `CRASTU_OFFLINE` (`1`, `true`, `yes`, `on` and `0`, `false`, `no`, `off`, any case); a non-empty environment value wins over the setting and an unrecognised one (a typo such as `ture`) counts as on, an empty or unset variable leaves the setting in charge, and a setting that is present but is not a boolean (null, a string, a number) or cannot be read counts as on; a missing key is off. When there is no data folder (no `HOME` and no `CRASTU_DATA`) and the variable is not set, the CLI reports that it cannot locate the setting instead of assuming online. The desktop app and the CLI find `settings.json` through one function, `crastu_settings::settings_path` (`CRASTU_DATA`, else the per-user folder of the platform), so a switch saved by one is read by the other. Models already on disk keep working; a missing one says how to get it. Slice 1 covers the gate, the setting, the downloader (`GatedFetch`) and the CLI; slice 2 adds the Settings switch in the UI and the MCP activity-log record of refusals, and each later network feature wires its own requests through the gate. The desktop app builds its gate as Offline ON when `settings.json` cannot be read (slice 2, tested). The shared data folder moves the Windows data folder to `%APPDATA%\Crastu` (the CLI used a Linux-style path there before); this is pre-1.0 and there is no migration. The socket path of `crastu-ipc` still follows its own rules and is not part of this lookup. |
| 31 | 2026-11-12 | Model sessions go through one registry in a new engine crate `crastu-ml`, independent of any runtime crate: a `SessionFactory` trait builds sessions, so the logic compiles for iOS and Android and is tested with a fake. | 33 | 2026-11-12 | Flight recorder (#25, slice 1): every recorded run keeps a local session folder `<root>/<app>/<UTC start>-<pid>/` (`crastu-recorder`, a core crate that compiles for mobile and uses no `unsafe`; redaction and name checks live in the small `crastu-redact` crate and the session files, lock, stream caps and retention in `crastu-logfiles`, so the recorder stays under the crate size limit). `end.json` records `status` (`ok`, `error`, `panicked`), `clean` (true only for `ok`), `panics`, `dropped_lines` and `duration_ms`; a folder without it ended badly. A caught panic in a thread is counted but does not stop an `ok` end, a panic after `finish` rewrites the file as `panicked`, and a panic out of `main` leaves none. `events.jsonl` is written one unbuffered write per line, because the point is surviving a crash; a failed write is counted and retried, not fatal. Liveness is an OS lock, not a guess from file times: each recorder holds an exclusive `File::try_lock` on `session.lock` for its lifetime, the system releases it when the process ends, and retention never deletes the current session or one whose lock cannot be taken (it still counts toward the limits). Where the file system has no locks, a session younger than an hour is alive, an older one is dead only with an `end.json`, and one without it counts as alive for a week. A session that is unlocked and has no `end.json` crashed and is kept only inside the normal limits (newest first, stop keeping once either limit is exceeded: at most 20 sessions and 50 MB, whichever is smaller, so the first session that does not fit and every older one are deleted; folders named like sessions only). Privacy is structural first: job and MCP events accept only a plain name (letters, digits, `_:-`, never a path) and an enum, perf job kinds go through a checked constructor, and the app name must be a plain name so it cannot leave the root. Free-text log and panic messages are only length-limited and redacted for known key shapes (API keys and tokens, JWTs, `Bearer`/`Basic`, URL userinfo, cookies, and the values of secret names found by their words, so `accessToken` and `private_key` count and `token_count` does not), shell flags, escaped JSON and PEM private keys; the redactor is a safety net whose exotic gaps are not blockers, because the guarantee is that job and MCP events are structured fields only, so the guarantee is "no known key shapes and no content fields", not "no user content" (callers must not pass content). The log root is `CRASTU_LOG_DIR` or a per-platform default; the `Recorder::start` override beats the variable; a settings entry is not added yet. Files are mode 0600 in a 0700 folder. When the folder cannot be created the recorder prints one stderr line and does nothing else. A live session is bounded: `events.jsonl` 20 MB and `perf.jsonl` 10 MB (one marker line, later lines dropped and counted), `panic.txt` five full reports, then one line per panic, 256 KB at most. Not in slice 1: the SIGSEGV/SIGBUS handler writing `crash.txt` (async-signal-safe, needs an opt-in crate that allows `unsafe`; slice 2) and Settings, About "Open logs" and "Copy diagnostics" (slice 3); the GUI and host perf feeds and MCP event wiring come with those. The machine model is left out of `session.json` until it can be read without a process spawn. Every test that starts a recorded command sets `CRASTU_LOG_DIR` to its own temporary folder, so a test run never writes to or prunes the real log folder. Slice 2 (2026-11-12): fatal signals (SIGSEGV, SIGBUS, SIGILL, SIGFPE, SIGABRT) write `crash.txt` (signal name and number, `si_code`, fault address when the kernel raised it, pid, session id, time) from an async-signal-safe handler in a new `os` crate, `crastu-crash`, which opts in to `unsafe` in one commented module, like `crastu-os-perms`; `crastu-recorder` stays safe and the CLI installs the handler with the recorder's `session_dir()`. Everything the handler needs is prepared at install time and the report is formatted without allocation; the file is opened with `O_EXCL|O_NOFOLLOW` (an existing file or symlink is never written through); only the first signal writes; the handler then chains to the previous handler (std's stack-overflow reporter, which aborts), restores the default action and re-raises, so the process still dies by the signal and the OS crash report still happens. A crash leaves no `end.json`. The calling thread gets an alternate signal stack if it has none. Unix only for now; Windows later. `libc` is the only new dependency (MIT or Apache-2.0, already in the lock file). Slice 3 (2026-11-13): the host and the desktop window both write `perf.jsonl` once a second (host: queue depth, job timings, memory where it can be read; GUI: frame p50/p99/max and memory), and Settings, About has Open logs and Copy diagnostics. Memory is read from `VmRSS` on Linux and Android at first (macOS and Windows follow in the #90 update below). A frame is the interval between two drawn frames of the root view, with intervals over 500 ms counted as pauses, not frames: a measure of how often and how steadily the window draws, not of how long one draw takes, until a hands-on comparison says it is good enough. Diagnostics are built from the recorder's own files only and go through the redactor a second time, are bounded (24 KB, 40 events, 12 lines per file, 300 characters per line) and put on the clipboard on the user's click; there is no upload. The log folder opens with the system's own opener, spawned with the path as one argument and never through a shell. Update 2026-11-13 (#90): resident memory in `perf.jsonl` is now read on macOS and Windows too, by the `os` crate `crastu-procmem` (`task_info` and `GetProcessMemoryInfo`, `unsafe` in one commented module, as with `crastu-crash`); because a `core` crate may not depend on an `os` crate and `crastu-recorder` allows no `unsafe`, the apps register the reader with `crastu_recorder::set_resident_reader`. |
